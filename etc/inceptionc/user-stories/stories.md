# TimeBack 유저 스토리

## 1. 작성 기준

- 핵심 사용자: 특정 직업이나 활동으로 한정하지 않은 일반 성인 스마트폰 사용자
- 구성: Epic → 독립적으로 검증 가능한 사용자 스토리 → Given/When/Then 인수 조건 → 요구사항 추적
- 시스템 동작: 별도 시스템 스토리로 분리하지 않고 관련 사용자 스토리의 인수 조건에 포함
- 우선순위: `P0`는 첫 번째 핵심 여정, `P1`은 다음 MVP 여정, `P2`는 MVP 데이터 관리 여정이다. 모든 항목은 MVP 범위다.
- 첫 번째 핵심 여정: 권한 허용 → 이벤트 수집 → Timeline 및 Context 수정 → 낭비시간 확인

## 2. Epic 1 — 앱 사용 맥락에서 낭비시간 발견

### US-01. Usage Access 권한 허용 — P0

사용자로서 앱 사용시간 분석에 필요한 권한을 허용하고 싶다. 그래야 TimeBack이 실제 사용 기록을 분석할 수 있다.

- 요구사항: FR-1.1, FR-1.2, NFR-3.3, NFR-4.1
- Given Android 14 이상 기기에서 Usage Access 권한이 없을 때, When 사용자가 권한 안내를 확인하면, Then 시스템은 권한 상태와 허용 방법을 표시해야 한다.
- Given 권한 안내 화면에서, When 사용자가 권한 허용 동작을 선택하면, Then 시스템은 Android의 해당 권한 설정으로 이동할 수 있게 해야 한다.
- Given 권한이 없거나 회수되었을 때, When 사용자가 주요 화면에 진입하려 하면, Then 시스템은 진입을 제한하고 권한 안내를 다시 표시해야 한다.
- Given 실제 Android 기기에서, When 권한을 허용·거부·회수하면, Then 각 상태 전환이 기기 시나리오 테스트로 검증되어야 한다.

### US-02. 원본 사용 이벤트 수집 — P0

사용자로서 허용한 범위의 앱 사용 이벤트가 자동으로 수집되기를 원한다. 그래야 기억에 의존하지 않고 사용 패턴을 확인할 수 있다.

- 요구사항: FR-1.3, FR-1.4, FR-10.5, NFR-3.3, NFR-4.1, NFR-4.4, NFR-5.1
- Given Usage Access 권한이 허용되었을 때, When 수집이 실행되면, Then 시스템은 `UsageStatsManager.queryEvents()`로 패키지명, 이벤트 종류, 발생 시각을 수집해야 한다.
- Given 이벤트가 수집되었을 때, When 원본 기록으로 저장하면, Then UsageEvent는 파생된 AppSession이나 Context와 구분되어야 한다.
- Given 이벤트 수집이 실행될 때, Then 시스템은 화면 내용, YouTube 내부 콘텐츠, 위치 또는 자동 오프라인 활동 정보를 수집하지 않아야 한다.
- Given 실제 Android 기기에서 앱을 전환했을 때, Then Foreground 및 Background 관련 이벤트 수집 결과를 검증할 수 있어야 한다.

### US-03. 신뢰 가능한 앱 세션 재구성 — P0

사용자로서 이벤트 목록이 실제 시작·종료 시각을 가진 앱 사용 세션으로 보이기를 원한다. 그래야 언제 얼마나 사용했는지 이해할 수 있다.

- 요구사항: FR-2.1, FR-2.2, FR-2.3, FR-2.4, NFR-2.2, NFR-3.1, NFR-5.1
- Given 서로 짝이 되는 Foreground와 Background 이벤트가 있을 때, When 세션을 생성하면, Then 패키지명, 시작 시각, 종료 시각, 사용시간을 가진 AppSession이 만들어져야 한다.
- Given 종료 짝이 없는 열린 이벤트가 있을 때, When 다음 앱 전환 또는 화면 종료 이벤트가 확인되면, Then 그 시각으로 세션을 닫아야 한다.
- Given 세션이 자정을 넘어갈 때, When 일간 집계를 만들면, Then 자정에서 세션을 나누고 각 날짜에 실제 포함된 시간만 배분해야 한다.
- Given 세션이 분할되었을 때, Then 분할된 사용시간의 합은 분할 전 실제 경과시간과 같아야 한다.

### US-04. 앱 기본 분류 설정 — P0

사용자로서 설치된 앱의 평소 사용 목적을 설정하고 싶다. 그래야 자동 Context 판정에 내 기준을 반영할 수 있다.

- 요구사항: FR-3.1, FR-3.2, FR-3.3, NFR-3.2, NFR-5.2
- Given 설치 앱 목록을 열었을 때, Then 사용자는 각 앱의 현재 기본 분류를 확인할 수 있어야 한다.
- Given 앱 하나를 선택했을 때, When `PRODUCTIVE`, `LEISURE`, `WASTE`, `NEUTRAL` 중 하나를 고르면, Then 선택한 기본 분류가 저장되어야 한다.
- Given 같은 앱에 기존 Context가 있을 때, When 기본 분류를 변경하면, Then 기본 분류와 사용자 확정 Context는 구분된 데이터로 유지되어야 한다.

### US-05. 실제 활동 직접 기록 — P0

사용자로서 공부·운동 같은 실제 활동을 시간대와 함께 기록하고 싶다. 그래야 같은 앱 사용도 당시 활동 맥락에 맞게 해석할 수 있다.

- 요구사항: FR-4.1, FR-4.2, FR-9.4, FR-10.5, NFR-2.2, NFR-3.2, NFR-5.1
- Given 활동 추가 화면에서, When 활동 종류와 시작·종료 시각을 입력하면, Then 운동, 공부, 개발, 독서, 여가 또는 사용자 정의 Activity가 저장되어야 한다.
- Given 활동이 자정을 넘어갈 때, When 날짜별 통계를 계산하면, Then 자정에서 나누어 실제 포함된 시간만 각 날짜에 배분해야 한다.
- Given 저장된 Activity가 있을 때, Then 원본 UsageEvent 및 AppSession과 구분된 데이터로 유지되어야 한다.

### US-06. 충돌 없는 Context 자동 판정 — P0

사용자로서 앱 세션과 실제 활동이 자연스럽게 겹치는 경우 자동으로 맥락이 반영되기를 원한다. 그래야 매번 직접 분류하지 않아도 된다.

- 요구사항: FR-5.1, FR-5.2, FR-5.3, NFR-2.1, NFR-3.1, NFR-5.1
- Given AppSession과 Activity의 시간대가 겹칠 때, When 두 분류가 충돌하지 않으면, Then 시스템은 실제 겹침 구간을 계산하고 활동을 우선한 Context를 생성해야 한다.
- Given 운동 60분과 그 안의 YouTube 50분이 겹칠 때, Then 실제 경과시간을 110분으로 합산하지 않아야 한다.
- Given Context가 생성되었을 때, Then AppSession, Activity 및 최종 Context는 구분된 데이터로 유지되어야 한다.

### US-07. 충돌 Context 확인 — P0

사용자로서 실제 활동과 앱 기본 분류가 충돌할 때 그 시간의 의미를 직접 확정하고 싶다. 그래야 공부 중 강의와 딴짓을 구분할 수 있다.

- 요구사항: FR-5.4, FR-5.5, FR-5.6, FR-5.7, NFR-3.2, NFR-5.2
- Given 활동 분류와 앱 기본 분류가 명백히 충돌할 때, When 자동 판정을 수행하면, Then 사용자 확인 전까지 Context를 `MIXED`로 유지해야 한다.
- Given 충돌이 발생했을 때, Then 시스템은 충돌하지 않는 중첩에는 질문하지 않고 해당 충돌에만 확인 질문을 표시해야 한다.
- Given 확인 질문이 표시되었을 때, When 사용자가 생산 목적, 보조 사용, 딴짓, 의도적 휴식 또는 기타 의미를 선택하면, Then 최종 분류와 사용자 확인 여부를 저장해야 한다.
- Given 사용자가 답하지 않았을 때, Then Context는 확인되지 않은 `MIXED` 상태로 남아야 한다.

### US-08. 일간 Timeline 확인 — P0

사용자로서 하루 동안 앱과 실제 활동이 어떻게 겹쳤는지 시간순으로 보고 싶다. 그래야 독립적인 낭비와 복합 활동을 구분할 수 있다.

- 요구사항: FR-6.1, FR-6.2, FR-6.3, FR-6.4, NFR-1.1, NFR-3.2
- Given 앱 세션, 활동 및 Context가 있을 때, When 사용자가 특정 날짜의 Timeline을 열면, Then 시작·종료 시각, 이름, 사용시간, 최종 분류가 시간순으로 표시되어야 한다.
- Given 다른 활동 중 앱을 사용한 구간이 있을 때, Then Timeline은 독립 앱 사용과 복합 활동을 구분해 표시해야 한다.
- Given 앱을 열거나 새로고침했을 때, Then 새 UsageEvent가 반영된 Timeline을 5초 이내에 표시해야 한다.
- Given 기기 현지 시간이 자정을 지났을 때, Then 각 기록은 해당 날짜에 실제 포함된 구간에 표시되어야 한다.

### US-09. 잘못된 Context 수정 — P0

사용자로서 Timeline에서 잘못 판정된 Context를 수정하고 싶다. 그래야 내 의도에 맞는 시간 통계를 유지할 수 있다.

- 요구사항: FR-5.8, NFR-2.3, NFR-3.2, NFR-5.2
- Given Timeline에 Context가 표시되었을 때, When 사용자가 최종 분류를 수정하면, Then 수정된 분류와 사용자 확인 상태가 저장되어야 한다.
- Given Context가 수정되었을 때, Then 관련 낭비시간, 확보한 시간, 되찾은 시간 및 리포트가 같은 판정 결과를 사용해야 한다.
- Given 앱 기본 분류가 바뀌더라도, Then 사용자 확정 Context는 앱 기본 분류와 구분되어야 한다.

### US-10. 낭비시간 확인 — P0

사용자로서 최종 Context를 기준으로 오늘의 낭비시간을 확인하고 싶다. 그래야 무의식적으로 흘려보낸 시간을 알 수 있다.

- 요구사항: FR-7.1, NFR-2.3, NFR-3.1
- Given 해당 날짜에 여러 Context가 있을 때, When 낭비시간을 계산하면, Then 최종 분류가 `WASTE`인 실제 경과시간만 합산해야 한다.
- Given 다른 활동과 겹친 앱 사용이 낭비에서 제외되도록 확정되었을 때, Then 그 구간은 낭비시간에 포함하지 않아야 한다.
- Given Context를 수정했을 때, Then 낭비시간 결과가 수정 내용과 일관되게 다시 계산되어야 한다.

## 3. Epic 2 — Baseline과 시간 변화 확인

### US-11. Baseline 관찰 상태 확인 — P1

사용자로서 최초 Baseline이 만들어지기까지 남은 기간을 알고 싶다. 그래야 아직 확보한 시간이 보이지 않는 이유를 이해할 수 있다.

- 요구사항: FR-7.2, FR-7.3, NFR-3.1
- Given 최초 Baseline이 없는 사용자일 때, When 낭비시간 데이터가 쌓이면, Then 시스템은 연속 7일 관찰 진행 상태를 유지해야 한다.
- Given 7일 관찰이 끝나지 않았을 때, Then 확보한 시간과 시간 회수율을 숨기고 남은 관찰 기간을 표시해야 한다.
- Given 연속 7일 관찰이 완료되었을 때, Then 평균 주간 낭비시간을 Baseline으로 생성해야 한다.

### US-12. Baseline 재산정 승인 — P1

사용자로서 기존 Baseline을 유지하면서 필요한 경우에만 재산정을 승인하고 싶다. 그래야 개선된 현재 사용량이 기준을 자동으로 낮추지 않는다.

- 요구사항: FR-7.4, NFR-3.2
- Given 최초 Baseline이 확정되었을 때, Then 시스템은 자동으로 그 값을 교체하지 않아야 한다.
- Given 시스템이 재산정을 제안했을 때, When 사용자가 승인하면, Then 새로운 관찰 결과로 Baseline을 재산정해야 한다.
- Given 사용자가 재산정을 승인하지 않았을 때, Then 기존 Baseline을 유지해야 한다.

### US-13. 확보한 시간 확인 — P1

사용자로서 Baseline보다 줄어든 낭비시간을 확보한 시간으로 확인하고 싶다. 그래야 개선 결과를 시간 단위로 이해할 수 있다.

- 요구사항: FR-7.5, NFR-2.3, NFR-3.1
- Given Baseline이 확정되고 현재 기간의 낭비시간이 더 적을 때, When 비교를 수행하면, Then 감소한 차이를 확보한 시간으로 계산해야 한다.
- Given 관련 Context가 수정되었을 때, Then 현재 낭비시간과 확보한 시간을 같은 데이터 기준으로 다시 계산해야 한다.

### US-14. 홈 대시보드 확인 — P1

사용자로서 오늘과 이번 주의 핵심 시간 지표를 한 화면에서 보고 싶다. 그래야 현재 변화와 목표 진행도를 빠르게 이해할 수 있다.

- 요구사항: FR-9.1, NFR-1.1, NFR-2.3, NFR-3.2
- Given 필요한 데이터가 있을 때, When 홈을 열면, Then 오늘의 낭비시간, Baseline 대비 변화, 확보한 시간, 되찾은 시간, 시간 회수율, 현재 목표 진행도를 표시해야 한다.
- Given Baseline 관찰이 완료되지 않았을 때, Then Baseline 기반 지표 대신 남은 관찰 기간을 표시해야 한다.
- Given 앱을 열거나 새로고침했을 때, Then 새 UsageEvent가 반영된 대시보드를 5초 이내에 표시해야 한다.

### US-15. 기간별 리포트 확인 — P1

사용자로서 일간·주간·월간 시간 사용 결과와 목표별 성과를 보고 싶다. 그래야 단기 변화와 누적 성취를 확인할 수 있다.

- 요구사항: FR-9.2, FR-9.3, FR-9.4, FR-9.5, NFR-2.3, NFR-3.2
- Given 주간 데이터가 있을 때, When 주간 리포트를 열면, Then 낭비시간, Baseline, 확보한 시간, 목표별 되찾은 시간 합계, 시간 회수율을 표시해야 한다.
- Given 주간 집계를 계산할 때, Then 기기 현지 시간 기준 월요일 00:00부터 다음 월요일 00:00 직전까지를 한 주로 사용해야 한다.
- Given 자정을 넘는 활동이 있을 때, Then 날짜별 실제 포함 시간만 일간·주간·월간 집계에 반영해야 한다.
- Given 리포트 기간을 변경하면, Then 누적 되찾은 시간과 목표별 사용시간을 선택한 기간 기준으로 조회할 수 있어야 한다.

## 4. Epic 3 — 확보한 시간을 목표 활동으로 전환

### US-16. 목표 생성과 진행률 확인 — P1

사용자로서 더 투자하고 싶은 활동과 목표시간을 등록하고 싶다. 그래야 되찾은 시간을 구체적인 성취로 연결할 수 있다.

- 요구사항: FR-4.3, FR-4.4, FR-10.5, NFR-3.2, NFR-5.1
- Given 목표 생성 화면에서, When 이름과 목표시간을 입력하면, Then 새로운 Goal이 저장되어야 한다.
- Given 목표에 시간이 누적되었을 때, When 목표를 조회하면, Then 누적 투자시간과 진행률을 표시해야 한다.
- Given 목표가 저장될 때, Then Goal은 Activity와 RecoveredTime 기록과 구분된 데이터로 유지되어야 한다.

### US-17. 시간 되찾기 타이머 사용 — P1

사용자로서 목표를 선택하고 타이머로 활동 시간을 기록하고 싶다. 그래야 확보한 시간을 바로 목표 활동에 사용할 수 있다.

- 요구사항: FR-8.1, NFR-3.2
- Given 하나 이상의 목표가 있을 때, When 사용자가 목표를 선택하고 타이머를 시작하면, Then 시작 시각과 선택한 목표가 기록되어야 한다.
- Given 타이머가 실행 중일 때, When 사용자가 완료하면, Then 종료 시각과 실제 경과시간을 가진 기록이 생성되어야 한다.

### US-18. 목표 활동 시간 직접 기록 — P1

사용자로서 타이머를 켜지 못한 목표 활동을 직접 기록하고 싶다. 그래야 오프라인 활동도 되찾은 시간에 반영할 수 있다.

- 요구사항: FR-8.2, NFR-3.2
- Given 목표가 있을 때, When 사용자가 목표와 시작·종료 시각을 입력하면, Then `MANUAL` 방식의 목표 활동 기록이 저장되어야 한다.
- Given 타이머를 완료했을 때, Then 생성된 기록은 `TIMER` 방식으로 구분되어야 한다.

### US-19. 목표별 시간 누적 — P1

사용자로서 타이머와 직접 기록으로 수행한 시간이 목표에 누적되기를 원한다. 그래야 실제 투자시간을 확인할 수 있다.

- 요구사항: FR-8.3, FR-10.5, NFR-3.2, NFR-5.1
- Given 완료된 타이머 또는 직접 입력 기록이 있을 때, When 누적시간을 계산하면, Then 해당 목표의 누적 투자시간과 되찾은 시간에 반영해야 한다.
- Given RecoveredTime이 저장될 때, Then 기록 방법, 시작·종료 시각, 지속시간 및 Goal 연결을 유지해야 한다.
- Given 목표의 누적시간이 바뀌면, Then 목표 진행률도 같은 기록을 기준으로 갱신되어야 한다.

### US-20. 겹친 목표 활동 정리 — P1

사용자로서 같은 시간에 겹친 목표 활동을 대표 목표 하나로 정리하고 싶다. 그래야 실제 경과시간이 중복 누적되지 않는다.

- 요구사항: FR-8.5, NFR-2.4, NFR-3.1
- Given 목표 활동 기록 두 개 이상이 겹칠 때, When 누적을 계산하면, Then 겹친 구간의 합집합을 한 번만 계산해야 한다.
- Given 겹친 기록이 발견되었을 때, When 사용자가 대표 목표를 선택하면, Then 겹친 시간은 대표 목표에만 누적되어야 한다.

### US-21. 되찾은 시간과 회수율 확인 — P1

사용자로서 목표 활동으로 전환한 전체 시간과 회수율을 확인하고 싶다. 그래야 확보한 시간을 얼마나 실제 행동으로 바꿨는지 알 수 있다.

- 요구사항: FR-8.4, FR-8.6, NFR-2.3, NFR-3.1
- Given 확보한 시간과 되찾은 시간이 있을 때, When 회수율을 계산하면, Then 되찾은 시간을 확보한 시간으로 나눈 비율을 표시해야 한다.
- Given 되찾은 시간이 확보한 시간을 초과했을 때, Then 되찾은 시간을 모두 유지하고 100%를 초과한 회수율을 표시할 수 있어야 한다.
- Given 관련 목표 활동이나 Context가 수정되었을 때, Then 되찾은 시간과 회수율을 일관되게 다시 계산해야 한다.

## 5. Epic 4 — 익명 백업과 데이터 통제

### US-22. 로그인 없는 익명 사용 — P2

사용자로서 계정을 만들지 않고 TimeBack을 사용하고 싶다. 그래야 로그인 절차 없이 개인 시간 기록을 시작할 수 있다.

- 요구사항: FR-10.1, FR-10.5, NFR-4.2
- Given 처음 앱을 사용하는 경우, When 사용자 데이터 영역을 생성하면, Then 로그인 계정 대신 익명 사용자 식별자로 구분해야 한다.
- Given 사용자 데이터가 생성될 때, Then User와 앱 사용·활동·Context·목표·회수 기록의 연결을 유지해야 한다.

### US-23. 익명 데이터 서버 백업 — P2

사용자로서 내 기록이 익명 식별자로 서버에 백업되기를 원한다. 그래야 앱 데이터의 백업 상태를 유지할 수 있다.

- 요구사항: FR-10.2, NFR-4.2, NFR-3.2
- Given 익명 사용자 데이터가 있을 때, When 백업이 실행되면, Then 데이터는 로그인 계정이 아니라 해당 익명 식별자에 연결되어야 한다.
- Given 백업이 성공했을 때, Then 해당 백업 시도가 완료된 것으로 기록되어야 한다.
- Given 백업 전송이 실패했을 때, Then 실패한 시도를 완료로 처리하지 않고 다시 시도할 수 있어야 한다.

### US-24. 기록 보관 기간 선택 — P2

사용자로서 내 사용 기록의 보관 기간을 선택하고 싶다. 그래야 원하는 기간만 데이터를 유지할 수 있다.

- 요구사항: FR-10.3, NFR-4.3, NFR-3.2
- Given 데이터 관리 화면에서, When 사용자가 제공되는 보관 기간 중 하나를 선택하면, Then 선택값이 저장되어야 한다.
- Given 보관 기간이 적용될 때, Then 원본 UsageEvent와 해당 기간 정책의 적용 대상인 파생 데이터에 같은 사용자 선택을 적용해야 한다.

### US-25. 전체 데이터 즉시 삭제 — P2

사용자로서 내 모든 TimeBack 데이터를 즉시 삭제하고 싶다. 그래야 앱 사용을 끝낼 때 기록을 남기지 않을 수 있다.

- 요구사항: FR-10.4, NFR-4.3, NFR-3.2
- Given 전체 삭제를 요청했을 때, When 사용자가 삭제를 확정하면, Then 원본 UsageEvent, 파생 데이터, 활동, Context, 목표 및 회수 기록을 삭제해야 한다.
- Given 서버 백업 데이터가 있을 때, Then 같은 익명 사용자 식별자에 연결된 백업도 전체 삭제 대상에 포함해야 한다.
- Given 삭제 작업 일부가 실패했을 때, Then 모든 대상이 삭제되기 전에는 전체 삭제 완료로 표시하지 않아야 한다.
