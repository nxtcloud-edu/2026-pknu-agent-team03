# TimeBack 작업 단위 설계

## 1. 확정 결정

- 공식 CONSTRUCTION 작업 단위는 `timeback-mvp` 하나다.
- 문서 폴더는 `aidlc-docs/construction/timeback-mvp/` 하나만 사용한다.
- `shared-contracts`, `track-device-data`, `track-domain-engine`, `track-ui`, `track-backup-server`는 별도 작업 단위나 별도 단계가 아니라 한 작업 단위 내부의 책임 구분이다.
- 네 책임 트랙은 공통 계약과 테스트 대역을 기준으로 같은 활성 작업 단위에 동시에 기여할 수 있다.
- CONSTRUCTION STEP 01부터 STEP 05까지는 `timeback-mvp`에 대해 각각 한 번씩 게이트를 통과한다.
- STEP 05의 통합 순서는 필수 규칙인 업무 규칙 → API → 저장 → 화면을 유지한다.
- 내부 통합 완료 판정은 승인된 M1 → M2 → M3 → M4 순서로 기록한다.
- 기술 스택은 이 문서에서 선택하지 않고 CONSTRUCTION STEP 02에서만 결정한다.

## 2. 공식 작업 단위

| 항목 | 내용 |
|---|---|
| ID | UOW-01 |
| 이름 | `timeback-mvp` |
| 목표 | Android 기기에서 낭비시간을 발견하고 Baseline·목표 활동·회수율을 확인하며 익명 서버 백업과 데이터 통제를 사용할 수 있는 통합 MVP 완성 |
| 선행 작업 단위 | 없음 |
| 포함 스토리 | US-01–US-25 전체 |
| 포함 구성 요소 | OS-01–OS-05, APP-01–APP-13, SRV-01–SRV-03, UI-01–UI-08 전체 |
| 공식 문서 폴더 | `aidlc-docs/construction/timeback-mvp/` |
| 코드 위치 | 워크스페이스 루트 `src/` |
| 인프라 설계 | 실행 · 익명 백업 서버와 격리 실행 환경 포함 |
| 종료 시점 | STEP 01–05 결과 승인과 단위 종료 조건 충족 |

### 포함 범위

- Usage Access 권한, UsageEvent 수집, 세션 재구성, 자정 분할
- 앱 분류, 실제 활동, Context 자동 판정·확인·수정
- Timeline, 낭비시간, 7일 Baseline, 확보한 시간, 대시보드, 리포트
- 목표, 타이머, 직접 기록, 중첩 제거, 되찾은 시간, 회수율
- 하드웨어 기반 익명 식별자 검증, 자동 백업, 재시도, 보관 기간, 전체 삭제
- UI-01–UI-08의 정상·로딩·빈 상태·오류 상태
- 자동 검증, 격리 서버 통합 검증, 실제 Android 기기 검증 경계

### 제외 범위

- 승인된 MVP 제외 기능
- iOS 완전 지원, 콘텐츠 내부 판별, 화면 내용·위치 수집
- 개인화 추천, AI 설명, 알림, 앱 제한, 외부 건강·캘린더 연동
- CONSTRUCTION STEP 02 승인 전의 언어·프레임워크·런타임·데이터베이스·배포 제품 결정

## 3. 네 명의 책임 트랙

| 담당 | 책임 트랙 | 주 책임 | 주 구성 요소 | 독립 시작 수단 |
|---|---|---|---|---|
| 1번 | `track-device-data` | Android 권한·이벤트·화면 상태·시간 경계, 세션 재구성, 기기 기준 저장 계약과 실제 저장 연결 | OS-01–OS-03, OS-05, APP-01, APP-03, APP-04, APP-11 | 고정 UsageEvent와 제어 시간, 저장 계약 테스트 대역 |
| 2번 | `track-domain-engine` | 앱·활동 분류, Context, 낭비시간, Baseline, 확보·목표·회수 계산 | APP-05–APP-09 | 가짜 세션·활동·저장소·시간을 사용한 순수 업무 규칙 입력 |

### 공통 책임

- 네 명 모두 자기 트랙의 업무 규칙, 오류 사례, 자동 검증을 함께 만든다.
- 공통 계약을 바꾸려면 영향을 받는 트랙을 먼저 표시하고 네 트랙의 테스트 대역과 실제 구현을 함께 갱신한다.
- APP-11은 1번이 공통 저장·변경 계약을 관리하고, 2번과 4번은 자기 도메인 데이터 요구를 그 계약으로 확장한다.
- 3번은 APP-11을 직접 호출하지 않고 합의된 기능 호출·조회 계약만 사용한다.
- 통합 체크포인트의 예상·실제 결과와 미완료 위험은 네 명이 공동으로 확인한다.

## 4. 병렬 작업을 가능하게 하는 공통 계약

공통 계약은 별도 작업 단위가 아니다. `timeback-mvp`의 CONSTRUCTION STEP 01에서 먼저 정의하고 같은 단계의 산출물 안에 둔다.

| 계약 ID | 계약 범위 | 제공 측 | 사용 측 | 계약이 고정되면 가능한 병렬 작업 |
|---|---|---|---|---|
| CT-01 | UsageEvent, AppSession, Activity, Context의 시간 구간과 상태 | 기기 데이터·도메인 | 도메인·UI | 실제 기기 입력 없이 세션·Context·Timeline 개발 |
| CT-02 | Goal, RecoveredTime, Baseline 및 시간 지표 | 도메인 | UI·기기 데이터 | 목표 화면과 리포트를 가짜 결과로 개발 |
| CT-03 | 엔터티별 저장·조회·변경 통지 | 기기 데이터 | 도메인·백업 서버 | 실제 저장 제품 없이 업무 규칙과 백업 변경 개발 |
| CT-04 | 사용자 작업, 조회 결과, 로딩·빈 상태·오류 상태 | 도메인·기기 데이터·백업 서버 | UI | 실제 기능 완료 전 UI-01–UI-08 개발 |
| CT-05 | 익명 식별자, 백업 변경, 성공·실패·삭제 상태 | 백업 서버·기기 데이터 | 기기 데이터·UI | 실제 서버와 앱 백업 클라이언트의 독립 개발 |
| CT-06 | 고정 이벤트, 제어 시간, 가짜 저장소, 가짜 서버 응답 | 모든 트랙 | 모든 트랙 | 앞 트랙 완료를 기다리지 않는 자동 검증 |

### 계약 운영 규칙

- 공통 계약에는 업무 의미와 입력·출력·오류만 정의하고 구현 제품을 넣지 않는다.
- 각 트랙은 실제 의존 대상이 준비되기 전 CT-06 테스트 대역을 사용한다.
- 테스트 대역과 실제 구현은 같은 계약 검증을 통과해야 한다.
- 계약 변경은 조용히 적용하지 않고 영향받는 스토리, 구성 요소, 테스트를 함께 수정한다.
- 트랙별 작업은 동시에 준비할 수 있지만 공식 산출물과 게이트는 `timeback-mvp` 하나로 합쳐 관리한다.

## 8. 내부 통합 체크포인트

체크포인트는 별도 작업 단위나 별도 게이트가 아니다. 트랙들이 병렬로 준비한 결과를 공식 마일스톤 순서로 통합 확인하는 지점이다.

| 체크포인트 | 통합 범위 | 선행 조건 | 완료 증거 |
|---|---|---|---|
| CP-0 공통 계약 | CT-01–CT-06 | STEP 01 기능 설계 승인 | 네 트랙의 같은 계약 사용과 테스트 대역 정의 |
| CP-1 M1 핵심 여정 | US-01–US-10 | CP-0 | 권한 → 이벤트 → 세션 → Context → Timeline → 낭비시간 통합 결과 |
| CP-2 M2 Baseline·리포트 | US-11–US-15 | CP-1 | 제어 시간 기반 7일 Baseline과 홈·기간 리포트 결과 |
| CP-3 M3 목표·회수 | US-16–US-21 | CP-2 | 목표·타이머·중첩·100% 초과 회수율 결과 |
| CP-4 M4 백업·통제 | US-22–US-25 | CP-3 | 격리 서버의 백업·재시도·보관·전체 삭제 결과 |
| CP-5 전체 통합 | US-01–US-25 | CP-1–CP-4 | 모든 논리 검증 진입점과 전체 사용자 여정 결과 |

백업 서버 트랙과 UI 트랙은 CP-1–CP-3 완료를 기다리지 않고 CT-04–CT-06으로 작업할 수 있다. 다만 최종 완료 증거는 승인된 마일스톤 순서로 누적한다.

## 10. 하드웨어 기반 익명 식별자 위험 게이트

- `track-backup-server`는 CONSTRUCTION STEP 02에서 Android 14 이상과 대상 기기 조건의 하드웨어 식별원 접근 가능성, 재실행·업데이트 후 안정성, 개인정보 영향을 검증한다.
- 검증 중에는 원본 하드웨어 값을 서버로 보내거나 영구 저장하지 않는다.
- 다른 트랙은 CT-05의 가짜 익명 식별자를 사용하므로 검증 결과를 기다리지 않고 설계와 테스트를 진행할 수 있다.
- 요구한 안정성이나 접근 가능성을 충족하지 못하면 해당 사실을 실패 증거로 남기고 STEP 02 게이트 2 전에 진행을 멈춘다.
- 이 경우 임의 식별자 등으로 자동 대체하지 않고 요구사항 변경 승인을 요청한다.
- 승인된 대체 방식이 없으면 APP-02, APP-12–APP-13, SRV-01–SRV-03의 코드 생성을 시작하지 않는다.

## 11. 논리 검증 진입점 배정

| 논리 이름 | 주 책임 트랙 | 통합 범위 |
|---|---|---|
| `verify-domain` | 도메인 | 세션 입력을 포함한 Context, Baseline, 확보·회수시간 규칙 |
| `verify-data` | 기기 데이터 | 기기 저장 생성·수정·삭제·재계산 및 변경 통지 |
| `verify-device` | 기기 데이터 | Android 14 이상 권한·UsageEvent·화면 상태·식별원 시나리오 |
| `verify-backup` | 백업 서버 | 익명 백업 성공·실패·재시도·보관·전체 삭제 |
| `verify-ui` | UI | UI-01–UI-08과 가짜·실제 기능 계약의 화면 흐름 |
| `build-debug` | 전체 공동 | 설치 가능한 디버그 산출물 |
| `verify-all` | 전체 공동 | 앱·서버 전체 빌드와 자동·통합 검증 |

정확한 명령은 CONSTRUCTION STEP 02에서 기술 스택을 확정한 뒤 연결한다.

## 12. 단위 종료 조건

- `timeback-mvp`의 CONSTRUCTION STEP 01–05가 각각 게이트 2 승인을 받아야 한다.
- US-01–US-25가 하나의 주 구현 트랙과 인수 검증 증거에 연결되어야 한다.
- OS-01–OS-05, APP-01–APP-13, SRV-01–SRV-03, UI-01–UI-08이 실제 구현 또는 승인된 검증 경계에 연결되어야 한다.
- CT-01–CT-06의 테스트 대역과 실제 구현이 같은 계약 검증을 통과해야 한다.
- CP-1–CP-4의 사용자 결과가 M1 → M2 → M3 → M4 순서로 통합 확인되어야 한다.
- 세션·Context·Baseline·목표 중첩·회수율 규칙의 자동 검증이 통과해야 한다.
- 격리된 로컬 서버에서 익명 백업, 실패 후 재시도, 보관 기간, 전체 삭제 통합 검증이 통과해야 한다.
- 실제 Android 14 이상 기기가 연결되어 있으면 권한과 UsageEvent 시나리오를 실행하고, 없으면 사용자 수동 체크리스트와 NFR-3.3 미완료 상태를 남겨야 한다.
- 전체 삭제는 기기와 서버 양쪽 완료가 확인되기 전 성공으로 표시되지 않아야 한다.
- CONSTRUCTION STEP 06에서 `build-debug`와 `verify-all` 결과, 설치 산출물, 전체 소스, 검증 요약을 남길 수 있는 상태여야 한다.
