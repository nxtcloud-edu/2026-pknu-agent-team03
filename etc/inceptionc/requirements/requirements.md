## 1. Functional Requirements

### FR-1: Usage Access 권한과 사용 이벤트 수집

- **FR-1.1**: 시스템은 Android 14 이상 기기에서 Usage Access 권한을 안내하고 권한 상태를 확인할 수 있어야 한다.
- **FR-1.2**: Usage Access 권한이 없거나 회수된 경우 시스템은 권한을 허용할 때까지 주요 화면 진입을 제한해야 한다.
- **FR-1.3**: 시스템은 Android `UsageStatsManager.queryEvents()`를 사용하여 패키지명, 이벤트 종류, 발생 시각을 포함한 원본 UsageEvent를 수집할 수 있어야 한다.
- **FR-1.4**: 시스템은 Foreground 및 Background 관련 UsageEvent를 사용자별 원본 기록으로 보관할 수 있어야 한다.

### FR-2: 앱 사용 세션 재구성

- **FR-2.1**: 시스템은 Foreground 및 Background 이벤트를 연결하여 패키지명, 시작 시각, 종료 시각, 사용시간을 가진 AppSession을 생성해야 한다.
- **FR-2.2**: Foreground 또는 Background 짝이 없는 이벤트는 다음 앱 전환 또는 화면 종료 이벤트 시각으로 세션을 닫아야 한다.
- **FR-2.3**: 자정을 넘어가는 AppSession은 자정에서 분할하여 각 날짜에 실제로 포함된 시간만 배분해야 한다.
- **FR-2.4**: 시스템은 앱별 총 사용시간뿐 아니라 각 세션의 실제 발생 시간대를 유지해야 한다.

### FR-3: 앱 기본 분류 관리

- **FR-3.1**: 사용자는 설치된 앱 목록에서 각 앱의 기본 분류를 설정하고 수정할 수 있어야 한다.
- **FR-3.2**: 앱 기본 분류는 `PRODUCTIVE`, `LEISURE`, `WASTE`, `NEUTRAL` 중 하나여야 한다.
- **FR-3.3**: 앱 기본 분류는 기본값으로만 사용되며 같은 앱도 시간대별 Context에 따라 다른 최종 분류를 가질 수 있어야 한다.

### FR-4: 실제 활동 기록과 목표 관리

- **FR-4.1**: 사용자는 활동 종류, 시작 시각, 종료 시각을 입력하여 오프라인 활동을 직접 기록할 수 있어야 한다.
- **FR-4.2**: 활동 종류는 운동, 공부, 개발, 독서, 여가 및 사용자 정의 활동을 표현할 수 있어야 한다.
- **FR-4.3**: 사용자는 이름과 목표시간을 가진 목표를 생성할 수 있어야 한다.
- **FR-4.4**: 시스템은 목표별 누적 투자시간과 진행률을 표시할 수 있어야 한다.

### FR-5: Context 생성과 충돌 확인

- **FR-5.1**: 시스템은 AppSession과 실제 활동의 시간 중첩 구간을 계산하여 Context를 생성해야 한다.
- **FR-5.2**: 시스템은 동일한 실제 경과시간에 겹친 활동과 앱 사용시간을 단순 합산하지 않아야 한다.
- **FR-5.3**: 활동과 앱 기본 분류가 충돌하지 않으면 활동을 우선하여 Context를 자동 판정해야 한다.
- **FR-5.4**: 활동과 앱 기본 분류가 명백히 충돌하면 사용자 확인 전까지 Context를 `MIXED`로 유지해야 한다.
- **FR-5.5**: 시스템은 활동 분류와 앱 기본 분류가 충돌할 때만 사용자에게 Context 확인 질문을 표시해야 한다.
- **FR-5.6**: 사용자는 확인 질문에서 생산 목적, 보조 사용, 딴짓, 의도적 휴식 또는 기타 의미를 선택하여 최종 Context를 확정할 수 있어야 한다.
- **FR-5.7**: 최종 Context 분류는 `PRODUCTIVE`, `LEISURE`, `WASTE`, `MIXED`, `NEUTRAL` 중 하나여야 하며 확인 여부를 함께 유지해야 한다.
- **FR-5.8**: 사용자는 Timeline에서 잘못 분류된 Context를 수정할 수 있어야 한다.

### FR-6: 일간 Timeline

- **FR-6.1**: 시스템은 앱 사용 세션, 실제 활동, 두 기록의 중첩 Context를 하루 단위 Timeline으로 표시해야 한다.
- **FR-6.2**: Timeline은 각 구간의 시작·종료 시각, 앱 또는 활동 이름, 사용시간, 최종 분류를 표시해야 한다.
- **FR-6.3**: Timeline은 앱 사용이 독립적인 낭비인지 다른 활동 중 발생한 복합 활동인지 구분해 표시해야 한다.
- **FR-6.4**: 일간 집계는 기기 현지 시간의 자정을 경계로 계산해야 한다.

### FR-7: 낭비시간과 Baseline

- **FR-7.1**: 시스템은 최종 Context가 `WASTE`로 확정된 실제 경과시간을 낭비시간으로 계산해야 한다.
- **FR-7.2**: 시스템은 최초 연속 7일의 낭비시간을 관찰하여 사용자의 평균 주간 Baseline을 생성해야 한다.
- **FR-7.3**: 최초 Baseline 관찰이 끝나기 전에는 확보한 시간과 시간 회수율을 숨기고 남은 관찰 기간을 표시해야 한다.
- **FR-7.4**: 최초 Baseline은 유지해야 하며, 재산정은 시스템이 제안하고 사용자가 승인한 경우에만 수행해야 한다.
- **FR-7.5**: 시스템은 Baseline보다 감소한 낭비시간을 확보한 시간으로 계산해야 한다.

### FR-8: 시간 되찾기와 회수율

- **FR-8.1**: 사용자는 목표 활동을 선택하여 시간 되찾기 타이머를 시작하고 완료할 수 있어야 한다.
- **FR-8.2**: 사용자는 타이머 또는 직접 입력 방식으로 목표 활동 시간을 기록할 수 있어야 한다.
- **FR-8.3**: 시스템은 기록된 목표 활동 시간을 목표별 누적시간과 되찾은 시간에 반영해야 한다.
- **FR-8.4**: 되찾은 시간은 확보한 시간을 초과해도 모두 기록해야 하며 시간 회수율은 100%를 초과할 수 있어야 한다.
- **FR-8.5**: 목표 활동 기록이 서로 겹치면 실제 경과시간의 합집합을 한 번만 누적하고 사용자가 대표 목표 하나를 선택할 수 있어야 한다.
- **FR-8.6**: 시스템은 확보한 시간이 존재할 때 되찾은 시간을 확보한 시간으로 나누어 시간 회수율을 계산해야 한다.

### FR-9: 대시보드와 리포트

- **FR-9.1**: 홈 대시보드는 오늘의 낭비시간, Baseline 대비 변화, 확보한 시간, 되찾은 시간, 시간 회수율, 현재 목표 진행도를 표시해야 한다.
- **FR-9.2**: 시스템은 이번 주 낭비시간, 주간 Baseline, 확보한 시간, 목표별 되찾은 시간 합계, 시간 회수율을 포함한 주간 리포트를 제공해야 한다.
- **FR-9.3**: 주간 집계는 기기 현지 시간 기준 월요일 00:00에 시작하여 다음 월요일 00:00 직전에 끝나야 한다.
- **FR-9.4**: 자정을 넘어가는 활동 기록은 자정에서 분할하여 각 날짜에 실제로 포함된 시간만 배분해야 한다.
- **FR-9.5**: 리포트는 일간·주간·월간 통계, Baseline 비교, 누적 되찾은 시간, 목표별 사용시간을 조회할 수 있어야 한다.

### FR-10: 익명 사용자와 데이터 관리

- **FR-10.1**: 시스템은 로그인 없이 익명 사용자 식별자로 사용자를 구분해야 한다.
- **FR-10.2**: 시스템은 익명 사용자 식별자에 연결된 앱 데이터를 서버에 백업할 수 있어야 한다.
- **FR-10.3**: 사용자는 사용 기록의 보관 기간을 선택할 수 있어야 한다.
- **FR-10.4**: 사용자는 원본 UsageEvent와 파생 데이터 및 목표 기록을 포함한 자신의 전체 데이터를 즉시 삭제할 수 있어야 한다.
- **FR-10.5**: 시스템은 User, App, UsageEvent, AppSession, Activity, Context, Goal, RecoveredTime 데이터를 서로 구분하여 관리해야 한다.

## 2. Non-Functional Requirements

### NFR-1: Performance

- **NFR-1.1**: 앱을 열거나 사용자가 새로고침한 뒤 새 UsageEvent가 반영된 Timeline과 대시보드를 5초 이내에 표시해야 한다.

### NFR-2: Correctness

- **NFR-2.1**: 중첩된 앱 사용과 실제 활동은 동일한 실제 경과시간을 중복 합산하지 않아야 한다.
- **NFR-2.2**: 자정을 넘는 세션과 활동을 분할한 각 날짜의 시간 합계는 분할 전 전체 실제 경과시간과 같아야 한다.
- **NFR-2.3**: Context 수정 결과는 낭비시간, 확보한 시간, 되찾은 시간 및 관련 리포트에 일관되게 반영되어야 한다.
- **NFR-2.4**: 목표 활동끼리 겹친 구간은 대표 목표에 한 번만 누적되어야 한다.

### NFR-3: Testing

- **NFR-3.1**: 세션 재구성, 시간 중첩, 자정 분할, Context 판정, Baseline, 확보한 시간 및 회수율 계산을 단위 테스트로 검증해야 한다.
- **NFR-3.2**: 주요 화면과 데이터 저장소 사이의 생성·수정·삭제 및 재계산 흐름을 통합 테스트로 검증해야 한다.
- **NFR-3.3**: 실제 Android 기기에서 Usage Access 권한 허용·거부·회수와 UsageEvent 수집 시나리오를 검증해야 한다.

### NFR-4: Security

- **NFR-4.1**: UsageEvent는 사용자가 Android Usage Access 권한을 허용한 경우에만 수집해야 한다.
- **NFR-4.2**: 서버 백업 데이터는 로그인 계정 대신 익명 사용자 식별자에만 연결해야 한다.
- **NFR-4.3**: 시스템은 사용자가 선택한 보관 기간과 전체 데이터 삭제 요청을 원본 및 파생 데이터에 동일하게 적용해야 한다.
- **NFR-4.4**: 시스템은 사용자가 보고 있는 화면 내용이나 YouTube 내부 콘텐츠를 수집하거나 감시하지 않아야 한다.

### NFR-5: Maintainability

- **NFR-5.1**: 원본 UsageEvent, 재구성된 AppSession, 사용자 Activity, 최종 Context 및 시간 회수 기록은 서로 독립된 데이터 개념으로 유지해야 한다.
- **NFR-5.2**: 앱 기본 분류와 사용자가 확정한 최종 Context는 서로 구분된 데이터 개념으로 유지해야 한다.

- 목표별 예상 완료 시점
- 알림 및 앱 사용 제한
- Health Connect 및 캘린더 연동
- AI 기반 패턴 설명
- iOS 완전 지원
- YouTube 내부 콘텐츠와 Shorts·일반 영상의 자동 구분
