## 1. Functional Requirements

### FR-1: 앱 사용 데이터 수집

- **FR-1.1**: Android UsageStatsManager 권한을 요청하고 허가 상태를 관리할 수 있어야 한다
- **FR-1.2**: queryEvents()를 통해 Foreground/Background 이벤트와 timestamp를 수집할 수 있어야 한다
- **FR-1.3**: 수집된 이벤트를 기반으로 앱별 사용 세션(AppSession: 시작시간, 종료시간, 지속시간)을 재구성할 수 있어야 한다

### FR-2: 앱 기본 분류 관리

- **FR-2.1**: 설치된 앱 목록을 표시하고 각 앱의 기본 분류(생산/의도적 여가/낭비/중립)를 설정할 수 있어야 한다
- **FR-2.2**: 기본 분류는 사용자가 언제든 변경할 수 있어야 한다

### FR-3: 활동 기록

- **FR-3.1**: 사용자가 오프라인 활동(운동, 공부, 개발 등)을 시작시간/종료시간과 함께 직접 기록할 수 있어야 한다
- **FR-3.2**: 기록된 활동은 해당 시간대의 앱 사용 Context 분석에 활용되어야 한다

### FR-4: Context 기반 시간 판정

- **FR-4.1**: 앱 사용 세션과 사용자 활동의 시간 중첩을 분석하여 Context를 생성할 수 있어야 한다
- **FR-4.2**: 활동과 겹치지 않는 앱 세션은 앱의 기본 분류대로 처리해야 한다
- **FR-4.3**: 복합 활동(운동 중 YouTube 등)은 하나의 Context로 처리하고 실제 경과시간을 초과하여 계산하지 않아야 한다
- **FR-4.4**: 사용자가 Timeline에서 잘못된 분류를 수정할 수 있어야 한다

### FR-5: 활동 충돌 확인

- **FR-5.1**: 활동 기록과 앱 사용 기록이 충돌할 경우 사용자에게 선택지를 제시하여 확인을 요청할 수 있어야 한다
- **FR-5.2**: 사용자의 응답을 기반으로 최종 분류(PRODUCTIVE/LEISURE/WASTE/MIXED/NEUTRAL)를 결정해야 한다

### FR-6: 낭비시간 계산

- **FR-6.1**: 최종 Context 판정 결과에서 WASTE로 분류된 시간을 합산하여 낭비시간을 계산해야 한다
- **FR-6.2**: 일별/주별 낭비시간을 조회할 수 있어야 한다

### FR-7: Baseline 관리

- **FR-7.1**: 초기 7일간 사용자의 평소 낭비시간을 측정하여 개인 Baseline을 생성해야 한다
- **FR-7.2**: 주간 낭비시간을 Baseline과 비교하여 확보한 시간(Saved Time)을 계산해야 한다

### FR-8: 목표 관리

- **FR-8.1**: 사용자가 목표 활동(개발, 공부, 운동, 독서 등)을 등록하고 목표시간을 설정할 수 있어야 한다
- **FR-8.2**: 각 목표의 누적 투자시간과 진행률을 조회할 수 있어야 한다

### FR-9: 시간 되찾기 (타이머)

- **FR-9.1**: 사용자가 목표 활동을 선택하고 타이머를 시작할 수 있어야 한다
- **FR-9.2**: 타이머 완료 시 해당 시간을 되찾은 시간(Recovered Time)으로 기록해야 한다
- **FR-9.3**: 수동 기록 방식으로도 되찾은 시간을 등록할 수 있어야 한다

### FR-10: 시간 회수율

- **FR-10.1**: 확보한 시간 대비 되찾은 시간의 비율(시간 회수율)을 계산하여 표시해야 한다

### FR-11: 메인 대시보드

- **FR-11.1**: 오늘의 낭비시간, Baseline 대비 증감, 오늘 되찾은 시간을 표시해야 한다
- **FR-11.2**: 이번 주 낭비시간, 확보한 시간, 실제 되찾은 시간, 시간 회수율을 표시해야 한다
- **FR-11.3**: 현재 목표 진행도를 표시해야 한다

### FR-12: Timeline 화면

- **FR-12.1**: 하루의 시간대별 앱 사용, 실제 활동, 복합 활동을 시각적으로 표시해야 한다
- **FR-12.2**: 각 항목에 낭비/생산/여가 상태를 색상 또는 아이콘으로 표시해야 한다

### FR-13: 주간 리포트

- **FR-13.1**: 매주 낭비시간, Baseline 비교, 확보시간, 되찾은 시간(목표별), 시간 회수율을 포함한 리포트를 생성해야 한다
- **FR-13.2**: 리포트 생성 시 푸시 알림으로 사용자에게 안내해야 한다

### FR-14: 실시간 알림

- **FR-14.1**: 낭비 시간이 임계치를 초과할 경우 사용자에게 실시간 경고 알림을 보낼 수 있어야 한다

### FR-15: 연속 사용 감지 및 리프레쉬

- **FR-15.1**: 낭비로 분류된 앱을 연속 1시간 이상 사용 시 경고 알림(오버레이 또는 푸시)을 표시해야 한다
- **FR-15.2**: 경고 시 미니게임 또는 상식 퀴즈를 표시하여 사용자가 무의식적 사용을 인식하고 리프레쉬할 수 있도록 해야 한다
- **FR-15.3**: 미니게임/퀴즈를 완료하면 앱 사용을 계속할지, 그만둘지 선택할 수 있어야 한다

### FR-16: 일일 피드백 문구

- **FR-16.1**: 하루가 끝나면 오늘의 낭비시간을 최근 7일 평균과 비교하여 피드백 문구를 표시해야 한다
- **FR-16.2**: 평균보다 좋으면 긍정 문구, 평균보다 나쁘면 격려 문구를 표시해야 한다
- **FR-16.3**: 문구는 다양하게 랜덤으로 출력되어야 한다 (반복 방지)

### FR-17: 인증

- **FR-17.1**: 앱 접근 시 간단한 로컬 PIN/비밀번호로 보호할 수 있어야 한다

## 2. Non-Functional Requirements

### NFR-1: Performance

- **NFR-1.1**: 앱 사용 세션 재구성은 하루치 이벤트 기준 3초 이내에 완료되어야 한다
- **NFR-1.2**: 메인 대시보드 로딩은 앱 실행 후 2초 이내에 데이터를 표시해야 한다

### NFR-2: Correctness

- **NFR-2.1**: 복합 활동 시간이 실제 경과시간을 초과하여 계산되어서는 안 된다
- **NFR-2.2**: Context 분류 결과는 사용자가 수정하기 전까지 일관성을 유지해야 한다

### NFR-3: Testing

- **NFR-3.1**: 시간 중첩 분석 로직과 낭비시간 계산 로직은 단위 테스트로 검증해야 한다
- **NFR-3.2**: API 엔드포인트는 통합 테스트로 검증해야 한다

### NFR-4: Security

- **NFR-4.1**: 사용자의 앱 사용 데이터는 서버 전송 시 암호화되어야 한다
- **NFR-4.2**: 로컬 PIN은 평문으로 저장하지 않고 해시 처리해야 한다

### NFR-5: Maintainability

- **NFR-5.1**: 비즈니스 규칙(분류 기준, Baseline 계산식 등)은 데이터(수치, 임계값)와 분리하여 관리해야 한다
- **NFR-5.2**: Android 클라이언트와 백엔드 API의 책임을 명확히 분리해야 한다

## 4. Out of Scope (MVP)

- iOS 완전 지원
- YouTube 내부 콘텐츠 자동 판별 (Shorts vs 일반 영상)
- 사용자가 실제로 무엇을 보고 있는지 화면 내용 감시
- 모든 오프라인 활동 자동 감지
- 위치 기반 행동 추적
- 반복 Context 자동 인식 (2차 기능)
- 개인화 행동 추천 (2차 기능)
- 시간대별 패턴 분석 (2차 기능)
- 목표별 예상 완료 시점 (2차 기능)
- 앱 사용 제한 (2차 기능)
- Health Connect 연동 (2차 기능)
- 캘린더 연동 (2차 기능)
- AI 기반 패턴 설명 (2차 기능)
