# TimeBack 애플리케이션 구성 요소 설계

## 1. 설계 결정

- Android 앱은 화면이 아니라 도메인 능력별 구성 요소로 나눈다.
- 기기 데이터가 기준 데이터이며 서버에는 백업 사본만 둔다.
- 로컬 데이터가 변경되면 자동으로 백업을 요청하고, 실패한 변경은 기기에 보관했다가 앱 시작 시 다시 시도한다.
- 네트워크가 없어도 수집·분석·목표·리포트 기능을 계속 제공하고 백업만 대기한다.
- 익명 사용자 식별자는 기기 하드웨어 정보에서 변환한다.
- 원본 하드웨어 값은 저장하거나 서버로 보내지 않고 변환된 식별자만 사용한다.
- 전체 삭제는 기기와 서버 삭제를 하나의 작업으로 추적하며 양쪽이 끝난 뒤에만 완료로 표시한다.
- 주요 화면은 책임, 사용 도메인, 상태, 사용자 동작, 오류·빈 상태까지 설계한다.
- 언어, 프레임워크, 런타임, 데이터베이스 제품, 배포 제품은 선택하지 않는다.

## 2. 전체 경계

```text
┌──────────────────── Android 운영체제 경계 ────────────────────┐
│ Usage Access 권한 · UsageStats 이벤트 · 화면 상태 · 현지 시간 │
│ 기기 하드웨어 식별원                                         │
└──────────────────────────┬─────────────────────────────────────┘
                           │ 운영체제 경계 인터페이스
┌──────────────────────────▼─────────────────────────────────────┐
│                       Android 앱                               │
│                                                               │
│ 권한·수집 → 세션 → 앱 분류·활동 → Context → 시간 지표        │
│                                         ↘ 목표·시간 회수       │
│                                                ↓              │
│                    Timeline·대시보드·리포트·설정 화면          │
│                                                ↓              │
│                 기기 기준 저장소 → 변경 기록 → 백업 조정      │
└──────────────────────────┬─────────────────────────────────────┘
                           │ 익명 식별자 + 백업 변경
┌──────────────────────────▼─────────────────────────────────────┐
│                    익명 백업 서버 경계                         │
│          백업 요청 처리 · 백업 사본 · 보관·삭제 처리          │
└────────────────────────────────────────────────────────────────┘
```

## 3. Android 운영체제 경계 구성 요소

| ID | 구성 요소 | 책임 | 제공하는 논리 인터페이스 |
|---|---|---|---|
| OS-01 | Usage Access Gateway | 권한 상태 확인과 설정 화면 이동을 Android 운영체제 경계로 격리 | 권한 상태 조회, 권한 설정 열기 |
| OS-02 | Usage Event Source | 허용된 기간의 패키지명, 이벤트 종류, 발생 시각 조회 | 기간별 UsageEvent 조회 |
| OS-03 | Screen State Source | 짝 없는 세션을 닫는 데 필요한 화면 종료 시각 제공 | 화면 종료 이벤트 조회 |
| OS-04 | Device Identity Source | 익명 식별자 생성에 사용할 기기 하드웨어 식별원 제공 | 안정적인 기기 식별원 읽기 |
| OS-05 | Time Source | 현지 시각, 자정, 월요일 경계와 테스트용 제어 시간 제공 | 현재 시각, 현지 시간대, 기간 경계 |

### 경계 규칙

- OS-01이 허용 상태를 반환하지 않으면 OS-02를 호출하지 않는다.
- OS-02는 화면 내용, 앱 내부 콘텐츠, 위치, 자동 오프라인 활동을 반환하지 않는다.
- OS-04에서 읽은 원본 하드웨어 값은 기기 저장소나 서버 요청에 직접 포함하지 않는다.
- OS-05를 통해서만 시간 계산 기준을 얻어 7일 Baseline과 경계 테스트를 제어할 수 있게 한다.

## 5. 서버 구성 요소

| ID | 구성 요소 | 책임 | 저장 범위 | 금지 사항 |
|---|---|---|---|---|
| SRV-01 | Anonymous Backup Boundary | 익명 식별자별 백업 변경 수신, 성공·실패 응답, 전체 삭제 요청 수신 | 요청 처리 상태 | 로그인 계정 요구, 기기 업무 규칙 재판정 |
| SRV-02 | Backup Copy Store | 기기 기준 데이터의 백업 사본 보관과 조회 | 변환된 익명 식별자 및 백업 데이터 | 원본 하드웨어 값 저장, 서버를 기준 데이터로 취급 |
| SRV-03 | Retention & Deletion Executor | 사용자 보관 선택 적용, 익명 식별자별 전체 백업 삭제 | 보관·삭제 실행 상태 | 기기 삭제 완료를 대신 확정 |

### 서버 경계 규칙

- 서버는 Context, Baseline, 회수율을 독립적으로 다시 판정하여 기기 값을 덮어쓰지 않는다.
- 서버는 변환된 익명 식별자를 불투명한 데이터 묶음 키로만 사용한다.
- 백업 실패는 기기 데이터 저장 성공을 되돌리지 않는다.
- 전체 삭제는 SRV-03의 삭제 완료가 확인될 때까지 기기 삭제 조정자에 성공으로 응답하지 않는다.

## 7. 화면 구성 요소

### UI-01. 권한·초기 진입

- 책임: Usage Access 필요성, 현재 권한 상태, 설정 이동, 주요 화면 접근 제어
- 사용하는 구성 요소: APP-01, APP-02
- 상태: 권한 확인 중, 권한 없음, 권한 허용됨, 권한 회수됨, 식별자 생성 실패
- 사용자 동작: 권한 설정 열기, 권한 상태 다시 확인
- 오류·빈 상태: 권한 미허용이면 주요 화면을 표시하지 않고 안내 유지

### UI-02. 홈 대시보드

- 책임: 오늘 낭비시간, Baseline 대비 변화, 확보·회수시간, 회수율, 목표 진행도 표시
- 사용하는 구성 요소: APP-08, APP-09, APP-10
- 상태: Baseline 관찰 중, 지표 표시, 새로고침 중, 데이터 없음, 계산 오류
- 사용자 동작: 새로고침, Timeline·목표·리포트 이동
- 오류·빈 상태: Baseline 미완료이면 확보시간·회수율 대신 남은 관찰 기간 표시

### UI-03. Timeline

- 책임: AppSession·Activity·Context 시간순 표시, 충돌 확인, Context 수정
- 사용하는 구성 요소: APP-04, APP-06, APP-07, APP-10
- 상태: 로딩, 데이터 없음, 정상 Timeline, MIXED 확인 대기, 수정 중, 오류
- 사용자 동작: 날짜 변경, Activity 추가·수정, Context 확인·수정, 새로고침
- 오류·빈 상태: 수집 이벤트가 없으면 빈 Timeline과 수집 조건 안내

### UI-04. 앱 관리

- 책임: 설치 앱 목록과 기본 분류 표시·수정
- 사용하는 구성 요소: APP-05
- 상태: 앱 목록 로딩, 정상 목록, 미분류 앱 있음, 목록 없음, 저장 오류
- 사용자 동작: 앱 선택, 기본 분류 변경
- 오류·빈 상태: 목록을 읽지 못하면 기존 저장 분류를 훼손하지 않고 오류 표시

### UI-05. 시간 되찾기

- 책임: 목표 선택, 타이머 시작·완료, 활동 직접 기록
- 사용하는 구성 요소: APP-09
- 상태: 목표 없음, 타이머 대기, 타이머 실행, 완료, 직접 입력, 중첩 확인, 오류
- 사용자 동작: 목표 선택, 시작, 완료, 직접 기록, 대표 목표 선택
- 오류·빈 상태: 목표가 없으면 목표 생성 이동 제공

### UI-06. 목표

- 책임: 목표 생성, 목표시간, 누적시간, 진행률 표시
- 사용하는 구성 요소: APP-09, APP-10
- 상태: 목표 없음, 목표 목록, 목표 상세, 저장 중, 오류
- 사용자 동작: 생성, 조회, 시간 기록으로 이동
- 오류·빈 상태: 목표 없음 상태에서 첫 목표 생성 동작 제공

### UI-07. 리포트

- 책임: 일·주·월 통계, Baseline 비교, 목표별 시간 표시
- 사용하는 구성 요소: APP-08, APP-09, APP-10
- 상태: 기간 선택, Baseline 미완료, 정상 리포트, 데이터 없음, 오류
- 사용자 동작: 기간 변경, 목표별 상세 조회
- 오류·빈 상태: 선택 기간에 데이터가 없으면 0과 미수집을 구분해 표시

### UI-08. 데이터 관리

- 책임: 익명 백업 상태, 보관 기간 선택, 전체 삭제 진행 상태 표시
- 사용하는 구성 요소: APP-02, APP-12, APP-13
- 상태: 백업 완료, 백업 대기, 백업 실패, 오프라인, 삭제 확인, 삭제 진행, 부분 실패, 삭제 완료
- 사용자 동작: 백업 상태 확인, 보관 기간 변경, 전체 삭제 요청·확정
- 오류·빈 상태: 기기와 서버 중 하나라도 삭제가 끝나지 않으면 전체 완료로 표시하지 않음

## 11. 품질 요구 반영

### 성능

- Timeline과 대시보드 조회는 서버 백업 완료를 기다리지 않는다.
- APP-10은 기기 기준 데이터에서 필요한 기간만 조회해 화면 새로고침 5초 기준을 검증할 수 있게 한다.
- 백업과 삭제 상태 조회는 핵심 시간 계산 경로와 분리한다.

### 정확성

- APP-04, APP-06, APP-07, APP-09는 모두 OS-05의 동일한 시간·기간 계약을 사용한다.
- 중첩 계산은 실제 구간 합집합을 기준으로 하며 화면에서 별도 합산하지 않는다.
- Context 수정 후 APP-08–APP-10이 같은 최종 Context를 사용한다.

### 테스트 가능성

- OS-02–OS-05는 고정 이벤트, 화면 종료, 하드웨어 식별원, 제어 시간으로 대체 가능한 경계다.
- APP-04, APP-07, APP-08, APP-09는 화면과 저장 제품 없이 규칙을 검증할 수 있는 책임을 가진다.
- APP-12와 SRV-01 경계는 성공, 네트워크 실패, 재시도를 반복 검증할 수 있어야 한다.

### 보안·개인정보

- 권한이 없으면 UsageEvent를 수집하지 않는다.
- 원본 하드웨어 값은 APP-02 변환 경계 밖으로 나가지 않는다.
- 서버는 로그인 계정이나 원본 하드웨어 값 없이 변환된 익명 식별자만 사용한다.
- 화면 내용, YouTube 내부 콘텐츠, 위치, 자동 오프라인 활동은 어떤 구성 요소도 수집하지 않는다.

### 유지보수

- UsageEvent, AppSession, Activity, Context, Goal, RecoveredTime의 저장 책임을 구분한다.
- 앱 기본 분류와 사용자 확정 Context를 별도 데이터로 유지한다.
- UI는 도메인 계산을 구현하지 않고 APP-03–APP-13의 결과와 작업만 사용한다.

## 15. 논리 데이터 계약 상세

이 절은 구현 데이터베이스나 전송 형식을 정하지 않고, 기존 APP-02–APP-13이 주고받아야 하는 논리 정보만 구체화한다. 앞 절의 데이터 소유권이 우선하며 이 절은 새 기준 데이터나 새 업무 규칙을 만들지 않는다.

### 15.1 공통 원칙

- 모든 시간 구간은 시작 시각을 포함하고 종료 시각을 포함하지 않는 구간으로 해석한다.
- 기간은 시작·종료 시각에서 계산할 수 있어야 하며, 저장된 기간과 계산 결과가 다르면 시작·종료 시각을 기준으로 재검증한다.
- 기기의 APP-11이 업무 데이터의 기준 소유자다. 서버의 같은 데이터는 복구를 위한 백업 사본이다.
- 원본 하드웨어 식별원은 논리 레코드와 백업 변경 어디에도 포함하지 않는다.
- Timeline, 홈 지표, 리포트는 APP-10이 기준 데이터에서 조립하는 조회 결과이며 별도의 기준 레코드가 아니다.
- 각 식별자는 같은 종류의 레코드를 구분하기 위한 논리 값이다. 생성 방식과 구현 자료형은 후속 단계에서 결정한다.

### 15.2 기기 기준 레코드

| 레코드 | 필드 | 의미 | 기준 소유·변경 책임 |
|---|---|---|---|
| User | `anonymousUserId`, `retentionSelection`, `createdAt` | 변환된 익명 식별자, 사용자가 고른 보관 설정, 최초 생성 시각 | APP-02·APP-13 → APP-11 |
| App | `packageName`, `displayName`, `defaultClassification`, `updatedAt` | 운영체제가 식별한 앱과 사용자가 관리하는 기본 분류 | APP-05 → APP-11 |
| UsageEvent | `eventId`, `anonymousUserId`, `packageName`, `eventType`, `occurredAt`, `collectedAt` | 운영체제에서 읽은 앱 사용 사건과 수집 시각 | APP-03 → APP-11 |
| AppSession | `sessionId`, `packageName`, `startAt`, `endAt`, `duration`, `sourceEventIds` | 연결·보정·분할을 마친 앱 사용 구간과 근거 사건 | APP-04 → APP-11 |
| Activity | `activityId`, `type`, `customName`, `startAt`, `endAt` | 사용자가 기록한 실제 활동 구간 | APP-06 → APP-11 |
| Context | `contextId`, `sessionId`, `activityId`, `startAt`, `endAt`, `classification`, `userConfirmed` | 세션과 활동의 관계로 판정·확정한 구간별 맥락 | APP-07 → APP-11 |
| Baseline | `baselineId`, `observationStart`, `observationEnd`, `baselineWasteDuration`, `status` | 관찰 범위, 기준 낭비시간, 관찰·확정 상태 | APP-08 → APP-11 |
| Goal | `goalId`, `name`, `targetDuration`, `createdAt` | 사용자가 정한 목표와 목표시간 | APP-09 → APP-11 |
| RecoveredTime | `recoveredId`, `goalId`, `method`, `startAt`, `endAt`, `duration` | 타이머 또는 직접 기록으로 남긴 목표 활동 구간 | APP-09 → APP-11 |

`Activity.customName`과 `Context.activityId`처럼 상황에 따라 값이 없을 수 있는 필드는 값 없음과 빈 문자열을 구분한다. `Context.userConfirmed`는 자동 판정과 사용자 확정 결과를 구분하기 위한 상태이며, UI가 별도의 판정 규칙을 만들기 위한 값이 아니다.

### 15.3 동기화·삭제 추적 레코드

| 레코드 | 필드 | 의미 | 기준 소유·변경 책임 |
|---|---|---|---|
| BackupChange | `changeId`, `entityType`, `entityId`, `operation`, `occurredAt`, `state`, `retryCount` | 저장 성공 뒤 생성되는 백업 변경과 전송·재시도 상태 | APP-12 / 기기 |
| DeletionJob | `jobId`, `requestedAt`, `deviceStatus`, `serverStatus`, `completedAt` | 기기·서버 전체 삭제를 하나로 추적하는 상태 | APP-13 / 기기, SRV-03은 서버 상태만 제공 |

- APP-11의 변경이 성공한 뒤에만 `BackupChange`를 만든다.
- 백업 성공은 해당 변경의 상태만 완료로 바꾸며 기기 기준 레코드의 소유권을 바꾸지 않는다.
- `DeletionJob.completedAt`은 기기와 서버 상태가 모두 완료일 때만 기록한다.
- 백업 대기 변경과 삭제 작업 상태는 업무 데이터의 백업 사본이 아니라 조정 상태다.

## 16. 핵심 사용자 흐름 상세

### 16.1 권한과 최초 진입 — US-01, US-22

```text
UI-01 진입
  → APP-01이 OS-01에서 현재 권한 확인
  ├─ 권한 없음: 필요성 안내와 설정 이동만 제공, 주요 화면 접근 제한
  └─ 권한 있음: APP-02가 OS-04의 식별원을 기기 안에서 변환
       ├─ 변환 성공: 익명 사용자 준비 후 홈 진입
       └─ 변환 실패: 기준을 임의로 바꾸지 않고 실패 상태 표시
```

권한 설정에서 돌아오면 현재 상태를 다시 읽는다. 이전 화면의 관측값만으로 허용을 가정하지 않는다.

### 16.2 일상 수집과 화면 갱신 — US-02–US-04, US-06, US-08, US-10, US-14

```text
사용자 새로고침 또는 앱 갱신 시점
  → APP-03이 마지막 수집 이후 UsageEvent 조회·저장
  → APP-04가 세션 연결·보정·기간 경계 분할
  → APP-05의 앱 기본 분류와 APP-06의 활동 조회
  → APP-07이 Context 판정
  → APP-08이 시간 지표 계산
  → APP-10이 Timeline과 홈 조회 결과 조립
  → UI-02·UI-03 표시
```

수집할 사건이 없으면 기존 데이터를 지우지 않는다. 화면은 데이터 없음, 최신 상태, 계산 오류를 서로 다른 상태로 표시한다.

### 16.3 활동·Context 확인과 수정 — US-05–US-09

```text
UI-03에서 Activity 생성·수정
  → APP-06 저장
  → APP-07이 영향 구간만 다시 판정
  ├─ 충돌 없음: 판정 결과 저장
  └─ 충돌 있음: MIXED와 확인 필요 상태 표시
       → 사용자가 Context 확정·수정
  → APP-08·APP-09 관련 지표 재계산
  → APP-10의 Timeline·홈·리포트 조회 결과 갱신
```

사용자 수정은 화면 표시값만 바꾸지 않고 APP-07의 최종 Context로 저장한다. 이후 모든 계산은 같은 최종 Context를 사용한다.

### 16.4 Baseline 관찰과 재산정 — US-11–US-13

```text
APP-08이 최종 Context를 날짜 경계에 맞춰 집계
  ├─ 관찰 미완료: 관찰 중 상태와 남은 범위 제공
  └─ 관찰 완료: Baseline 후보 제공
       → 사용자 승인 필요한 재산정이면 승인 대기
       → 승인 후 Baseline 저장
       → 확보한 시간 조회 결과 갱신
```

관찰 중 상태를 수치 결과로 대신하지 않는다. 재산정은 기존 기록을 지우는 동작이 아니라 승인된 기준을 다시 계산하는 동작이다.

### 16.5 목표와 시간 회수 — US-16–US-21

```text
UI-06에서 Goal 생성
  → UI-05에서 Goal 선택
  ├─ TIMER: 시작과 완료 시각으로 RecoveredTime 생성
  └─ MANUAL: 사용자가 입력한 실제 구간으로 RecoveredTime 생성
       → APP-09가 겹친 구간을 한 번만 계산
       → 여러 Goal이 겹치면 대표 Goal 확인
       → 누적시간·진행률·되찾은 시간·회수율 갱신
       → APP-10이 홈·목표·리포트 조회 결과 조립
```

타이머와 직접 기록은 입력 방식만 다르며 같은 `RecoveredTime` 계산 규칙을 사용한다.

### 16.6 기간 리포트 — US-15

```text
UI-07에서 기간 선택
  → APP-10이 기간 경계를 OS-05 계약에 맞춰 요청
  → APP-08의 Baseline·시간 지표와 APP-09의 목표 지표 조회
  ├─ Baseline 미완료: 비교 불가 상태 표시
  ├─ 기간 데이터 없음: 미수집과 계산된 0을 구분
  └─ 데이터 있음: 기간 통계와 목표별 결과 표시
```

리포트는 서버 백업 완료를 기다리지 않으며 기기 기준 데이터에서 재현한다.

### 16.7 백업·보관·전체 삭제 — US-23–US-25

```text
APP-11 로컬 변경 성공
  → APP-12가 BackupChange 생성
  ├─ 전송 성공: 해당 변경 완료
  └─ 오프라인·실패: 대기 유지, 로컬 기능 계속
       → 다음 앱 시작에서 재시도

UI-08 보관 설정 변경
  → APP-13이 기기 선택 저장과 서버 적용 상태 조정

UI-08 전체 삭제 확정
  → APP-13이 DeletionJob 생성
  ├─ APP-11 기기 데이터 삭제 상태
  └─ SRV-03 서버 백업 삭제 상태
       → 양쪽 완료 뒤에만 전체 완료
```

## 17. UI-01–UI-08 텍스트 와이어프레임

와이어프레임은 기존 여덟 화면의 정보 구조를 구체화한 것이다. 화면 이름과 기능 범위를 추가하지 않으며 문구와 시각 스타일은 후속 UI 설계에서 조정할 수 있다.

### UI-01. 권한·초기 진입

```text
┌─ TimeBack ───────────────────────────┐
│ 앱 사용 기록 권한이 필요한 이유       │
│ 수집하는 정보 / 수집하지 않는 정보    │
│                                      │
│ [현재 상태: 확인 중·미허용·허용]      │
│ [권한 설정 열기]  [상태 다시 확인]    │
│                                      │
│ 오류: 식별자 준비 실패 또는 권한 회수 │
└──────────────────────────────────────┘
```

- 미허용 상태에서는 홈으로 건너뛰는 동작을 제공하지 않는다.
- 허용 확인 뒤에만 주요 화면으로 이동한다.

### UI-02. 홈 대시보드

```text
┌─ 홈 ─────────────────────────────────┐
│ 오늘 낭비시간        [값 또는 상태]   │
│ Baseline 대비        [값 또는 관찰 중]│
│ 확보한 시간 / 회수시간 / 회수율       │
│                                      │
│ 목표 진행도          [목표별 상태]    │
│ [Timeline] [목표] [리포트]            │
│ [새로고침]                           │
└──────────────────────────────────────┘
```

- Baseline 관찰 중에는 비교 결과 자리에 관찰 상태를 표시한다.
- 로딩, 데이터 없음, 계산 오류를 같은 빈 카드로 합치지 않는다.

### UI-03. Timeline

```text
┌─ Timeline ───────────────────────────┐
│ [이전 날짜] [선택 날짜] [다음 날짜]  │
│                                      │
│ 시간 구간  앱 세션 / 실제 활동        │
│            Context [분류·확인 상태]   │
│            [확인] [수정]              │
│                                      │
│ [Activity 추가·수정] [새로고침]       │
└──────────────────────────────────────┘
```

- MIXED 구간에만 확인 동작을 강조한다.
- 사건이 없을 때는 빈 Timeline과 수집 조건 안내를 함께 표시한다.

### UI-04. 앱 관리

```text
┌─ 앱 관리 ────────────────────────────┐
│ [앱 검색·목록 영역]                   │
│ 앱 이름             기본 분류         │
│ 앱 항목             [분류 선택]       │
│                                      │
│ 상태: 로딩 / 미분류 있음 / 목록 없음  │
│ 오류: 기존 분류 유지, 다시 시도       │
└──────────────────────────────────────┘
```

- 변경 대상 앱과 저장 결과를 분명히 보여준다.
- 목록 읽기 실패가 기존 저장 분류의 삭제로 이어지지 않는다.

### UI-05. 시간 되찾기

```text
┌─ 시간 되찾기 ────────────────────────┐
│ 목표 선택             [선택된 목표]   │
│                                      │
│ 타이머                [대기·실행 상태]│
│ [시작] [완료]                         │
│                                      │
│ [직접 기록]  시작 / 종료              │
│ 중첩 시 [대표 목표 선택]              │
└──────────────────────────────────────┘
```

- 목표가 없으면 UI-06의 첫 목표 생성 동작으로 연결한다.
- 실행 중, 완료, 직접 입력, 중첩 확인, 저장 오류를 분리한다.

### UI-06. 목표

```text
┌─ 목표 ───────────────────────────────┐
│ [새 목표 만들기]                      │
│                                      │
│ 목표 이름     목표시간 / 누적시간     │
│               진행률                  │
│ [상세 보기]   [시간 기록으로 이동]    │
│                                      │
│ 상태: 목표 없음 / 저장 중 / 오류      │
└──────────────────────────────────────┘
```

- 목록과 상세는 APP-09·APP-10의 같은 목표 결과를 사용한다.
- 목표 없음 상태에서 첫 생성 동작을 바로 제공한다.

### UI-07. 리포트

```text
┌─ 리포트 ─────────────────────────────┐
│ [일] [주] [월]       [선택 기간]      │
│ 낭비시간 / Baseline 비교              │
│ 확보한 시간 / 되찾은 시간 / 회수율    │
│                                      │
│ 목표별 시간          [상세 보기]      │
│ 상태: 관찰 중 / 데이터 없음 / 오류    │
└──────────────────────────────────────┘
```

- 계산된 0과 수집되지 않은 상태를 다른 표시로 제공한다.
- Baseline 미완료이면 비교할 수 없는 항목을 명시한다.

### UI-08. 데이터 관리

```text
┌─ 데이터 관리 ────────────────────────┐
│ 익명 백업 상태       [완료·대기·실패] │
│ 네트워크 상태        [온라인·오프라인]│
│                                      │
│ 보관 기간            [승인된 선택값]  │
│ [보관 설정 변경]                     │
│                                      │
│ [전체 데이터 삭제]                   │
│ 삭제 상태: 기기 [ ] / 서버 [ ]       │
└──────────────────────────────────────┘
```

- 전체 삭제는 확인 단계를 거치며 기기·서버 상태를 각각 표시한다.
- 한쪽 실패를 전체 완료로 바꾸지 않고 부분 실패 상태로 유지한다.

## 18. 익명 백업 경계 계약 상세

이 절의 이름은 논리 동작을 가리키며 네트워크 경로, 직렬화 형식, 통신 제품을 결정하지 않는다. 모든 요청은 APP-12·APP-13에서 SRV-01·SRV-03 경계로만 전달된다.

| 논리 동작 | 기기에서 보내는 정보 | 서버가 돌려주는 정보 | 경계 규칙 |
|---|---|---|---|
| `SubmitBackupChanges` | 변환된 익명 식별자, `BackupChange` 묶음, 각 변경의 대상 레코드 사본 | 변경별 수락 또는 재시도 가능 실패 | 같은 `changeId`의 재전송을 중복 변경으로 적용하지 않도록 식별 |
| `ReadBackupStatus` | 변환된 익명 식별자, 확인할 변경 식별자 | 변경별 처리 상태 | 서버 상태는 APP-12의 대기·완료 판단에만 사용 |
| `ApplyRetentionSelection` | 변환된 익명 식별자, 사용자가 승인한 보관 선택 | 적용 상태 또는 실패 | 서버가 임의의 보관값으로 바꾸지 않음 |
| `RequestFullDeletion` | 변환된 익명 식별자, 삭제 작업 식별자 | 요청 수락 또는 실패 | 익명 식별자의 모든 백업 사본을 삭제 대상으로 지정 |
| `ReadDeletionStatus` | 변환된 익명 식별자, 삭제 작업 식별자 | 진행·완료·실패 상태 | 서버 완료는 서버 사본 삭제만 뜻하며 기기 삭제 완료를 대신하지 않음 |

### 18.1 성공·실패 처리

- 한 묶음에서 일부 변경만 수락되면 수락된 변경만 완료하고 나머지는 대기로 유지한다.
- 네트워크 오류나 서버 실패는 APP-11에 이미 저장된 기기 데이터를 되돌리지 않는다.
- 재시도할 때 동일 변경을 구분할 수 있도록 `changeId`를 유지한다.
- 백업 상태 조회가 실패해도 Timeline, 목표, 리포트 같은 로컬 기능은 계속 사용할 수 있다.
- 전체 삭제 재시도는 같은 `DeletionJob`을 이어가며 별개의 완료 작업으로 표시하지 않는다.

### 18.2 서버에서 하지 않는 일

- 원본 하드웨어 식별원을 받거나 저장하지 않는다.
- Context 충돌, Baseline, 목표 중첩, 확보시간, 되찾은 시간, 회수율을 독립적으로 계산하지 않는다.
- 백업 사본을 기기 데이터보다 우선하는 기준 데이터로 만들지 않는다.
- 사용자 계정 생성이나 로그인 성공을 백업의 선행 조건으로 두지 않는다.

## 19. 책임 트랙별 병렬 시작 자료

이 절은 `application-design/unit-of-work.md`의 단일 공식 작업 단위와 네 책임 트랙을 그대로 사용한다. 새 작업 단위나 별도 게이트를 만들지 않으며, 실제 CONSTRUCTION 시작 승인을 뜻하지 않는다.

| 책임 트랙 | 처음 고정해 사용할 계약 | 실제 의존 대상 전 사용할 입력·대역 | 다른 트랙에 제공할 결과 |
|---|---|---|---|
| `track-device-data` | CT-01 세션 구간, CT-03 저장·변경 통지 | 고정 UsageEvent, 화면 종료 사건, 제어 시간, 가짜 저장소 | AppSession, 저장 성공·실패, BackupChange 발생 조건 |
| `track-domain-engine` | CT-01 Context 입력, CT-02 시간 지표 | 고정 AppSession·Activity·분류, 가짜 저장소와 제어 시간 | 최종 Context, Baseline 상태, 목표·회수 계산 결과 |
| `track-ui` | CT-04 사용자 작업·조회·화면 상태 | UI-01–UI-08별 고정 조회 결과와 성공·빈 상태·오류 응답 | 화면 동작 결과와 계약별 호출 검증 |
| `track-backup-server` | CT-03 변경 통지, CT-05 백업·삭제 상태 | 가짜 익명 식별원, 고정 BackupChange, 성공·부분 실패·오프라인 응답 | 변경별 상태, 보관 적용 상태, 서버 삭제 상태 |

### 19.1 합치는 지점

| 연결 | 함께 확인할 계약 | 충돌 방지 기준 |
|---|---|---|
| 기기 데이터 ↔ 도메인 | CT-01, CT-03 | 시간 구간 해석과 저장 식별자를 한쪽에서 임의 변경하지 않음 |
| 도메인 ↔ UI | CT-02, CT-04 | UI가 시간 계산을 복제하지 않고 상태와 결과만 표시 |
| 기기 데이터 ↔ 백업 서버 | CT-03, CT-05 | 로컬 저장 성공과 백업 성공을 별도 상태로 유지 |
| 전체 ↔ UI | CT-04–CT-06 | 가짜 결과와 실제 결과가 같은 화면 상태 계약을 사용 |

세부 배정, 스토리 주 소유, 내부 체크포인트는 변경하지 않으며 `application-design/unit-of-work.md`를 최종 기준으로 삼는다.

## 20. inception2 선별 이식 검증

### 20.1 가져온 표현과 적용 결과

| 검토 영역 | 보수적으로 반영한 내용 | 기존 설계 보호 결과 |
|---|---|---|
| 데이터 모델 | APP-11 소유 레코드의 논리 필드와 조정 상태 | 새 데이터 소유자와 서버 기준 데이터를 만들지 않음 |
| 사용자 흐름 | 승인된 스토리의 시작·분기·오류·완료 흐름 | US-01–US-25 밖의 기능을 넣지 않음 |
| 화면 구조 | UI-01–UI-08의 정보 영역과 기존 상태 | 새 화면이나 별도 사용자 여정을 만들지 않음 |
| 백업 경계 | 익명 변경, 상태, 보관, 전체 삭제의 논리 계약 | 서버에 도메인 계산 책임을 넘기지 않음 |
| 병렬 준비 | CT-01–CT-06과 네 책임 트랙의 테스트 대역 연결 | `timeback-mvp` 단일 작업 단위와 배정을 유지 |

### 20.2 의도적으로 반영하지 않은 범위

- 승인된 요구사항에 없는 인증, 개입 기능, 오락 기능, 추가 사용자 피드백 기능
- 요구사항 근거가 없는 시간·개수·보관 기준값
- 서버가 기기 도메인 판정과 지표 계산을 대신하는 구조
- 네 책임 트랙을 서로 선행해야 하는 별도 작업 단위로 바꾸는 구조
- 후속 기술 검토 전에 특정 구현 제품을 선택하는 내용
- 제공 파일에 없는 실행 결과나 프로토타입을 존재한다고 간주하는 설명

### 20.3 충돌 시 우선순위

1. `requirements/requirements.md`의 승인 요구사항과 `user-stories/stories.md`의 승인 스토리
2. 작업 단위 수·책임 트랙·스토리 배정에는 STEP 07 최종 결과인 `application-design/unit-of-work.md`
3. 구성 요소·데이터 소유권·시스템 경계에는 이 문서의 기존 1–14절
4. 이 문서의 15–20절에 추가된 상세 표현

기존 14절의 STEP 07 전달 문구는 작업 단위를 확정하기 전에 작성된 예상이며, 확정된 작업 단위 판단에는 STEP 07 최종 결과를 적용한다. 따라서 공식 작업 단위는 `timeback-mvp` 하나이고 네 `track-*` 항목은 그 내부 책임 구분이다.

15–20절이 앞선 분야별 기준과 다르게 해석될 여지가 있으면 해당 기준을 적용하고 이 상세 표현을 수정한다. 선별 보강은 새 요구사항, 새 스토리, 새 구성 요소, 새 화면, 새 작업 단위를 승인하는 근거로 사용하지 않는다.
