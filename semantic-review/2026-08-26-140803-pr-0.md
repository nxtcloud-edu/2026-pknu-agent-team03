# APP-05~APP-09 Context·Baseline·시간 회수 기능 설계

Gate 1에서 승인된 Q1~Q14를 App Default/final Context 분리, 원자 구간 기반 Waste/Recovered 계산, 7일 Baseline, 대표 Goal 선택, UI 상태 계약으로 구체화한 변경이다. 저장된 Context의 유효 버전과 다중 관계의 최종 판정이 닫히지 않아 사용자 수정 뒤에도 과거 WASTE가 다시 집계될 수 있다. Baseline의 진행 중 기간과 MeasurementDay 갱신, Goal 진행률 범위, 대표 Goal 식별자에도 실제 수치를 바꾸는 계약 공백이 남아 있다. Java/JDK, 빌드 도구, DB, 프레임워크는 STEP 02로만 이관되어 승인되지 않은 기술 스택 선택은 발견되지 않았다.

Watch for: **[confirmed]** 대체된 Context의 유효 버전 부재, **[confirmed]** 현재 날짜의 Baseline 완전성 모순, **[confirmed]** 재분할 시 대표 Goal 선택 손실, **[confirmed]** 새 민감 파생 레코드의 보관·전체 삭제 누락.

**Verdict**: NEEDS_CHANGES

## High-level view

Context는 사용자 확정 우선순위를 선언하지만 현재 유효한 revision을 정하지 않는다. 한 AtomicSegment에서 관계별 Context를 여러 개 만들면서 segment 전체의 final classification도 정하지 않아, USER_CONFIRMED PRODUCTIVE와 AUTO WASTE가 공존하면 APP-08이 WASTE를 다시 합산할 수 있다.

Baseline은 완전한 현지 날짜만 유효하다고 하면서 오늘·현재 주에도 같은 expected Baseline 식을 적용한다. 현재 날짜는 종료 전 COMPLETE가 될 수 없어 `IN_PROGRESS`와 `DATA_INCOMPLETE`가 충돌하고, 같은 localDate 재기록이나 과거 Context 수정의 관찰 갱신 규칙도 없다.

Goal 화면의 누적 진행률과 리포트 기간 합계가 `accumulated(goal, P)` 하나로 섞여 있다. 대표 Goal 선택도 조회마다 파생되는 정확한 segment 좌표에 묶여 있어 query clipping이나 새 경계가 생기면 이전 선택을 재적용할 근거가 없다.

Timeline 조회 모델은 원자 display row와 고유 duration을 주지 않아 UI가 겹침·합집합을 재구성해야 한다. Recovery Rate 상태, 재계산 freshness, APP-05 설치 앱 입력, 타이머 삭제 통지에도 생산자와 소비자가 같은 결과를 만들기 어려운 불일치가 있다.

MeasurementDay, BaselineObservation/Candidate, RunningTimer, OverlapResolution은 민감한 파생 데이터지만 FR-10.3/10.4·NFR-4.3의 보관·백업·전체 삭제에 연결되지 않았다. 추적표도 실제로 설계한 FR-6/FR-9와 US-08/14/15 및 핵심 lifecycle 회귀 사례를 생략한다.

### High — 대체된 Context가 현재 집계에서 제외된다는 계약이 없다 [confirmed]

`domain-model.md` DM-12(144~175행)는 `supersedesContextId`를 두지만 active/effective 상태, revision 순서, 결정 시각 또는 current 선택 규칙이 없다. `business-rules.md` BR-07-06~07(169~176행)은 이전 Context를 감사 근거로 보존할 수 있다고 하고, `service-contracts.md` SC-D02·SC-07-01·SC-07-04(90~107, 225~297행)는 effective-only 기간 조회를 요구하지 않는다. BR-08-01(186~198행)은 `WASTE`이고 `AUTO_CLASSIFIED|USER_CONFIRMED`인 Context를 모두 집계한다.

```text
기존 USER_CONFIRMED WASTE
  └─ Timeline 수정 → 새 USER_CONFIRMED PRODUCTIVE
기간 조회 → 두 revision 모두 반환 가능
Waste union → 이전 WASTE가 계속 포함
```

FR-5.8, US-09/10, NFR-2.3을 보장하려면 revision/effective 상태와 결정 시각 또는 별도 ContextDecision history가 필요하다. APP-11은 current-effective Context만 지표 조회에 반환하고, 대체 저장과 current 전환을 원자화하며 WASTE→PRODUCTIVE 수정 후 재분석 회귀를 검증해야 한다.

### High — 관계별 Context가 같은 원자 구간에 상충된 final classification을 남긴다 [confirmed]

`business-rules.md` BR-07-02(125~133행)는 session/activity 조합별 후보를 만들고 BR-07-08(177~183행)은 `sessionId + activityId + atomic interval` 관계를 모두 보존한다. `domain-model.md` DM-11(132~143행)은 한 AtomicSegment에 여러 session/activity를 허용하지만 DM-12는 단일 관계만 표현하며, APP-08은 segment-level 결정을 받지 않고 WASTE Context union을 취한다.

```text
같은 atomic interval T
  Session + Activity-A → AUTO WASTE
  Session + Activity-B → USER_CONFIRMED PRODUCTIVE
BR-08-01 → WASTE 관계가 있으므로 T를 Waste에 포함 가능
```

Union은 중복 길이만 막을 뿐 US-10의 사용자 제외 결정을 보장하지 않는다. 관계 증거와 지표용 effective segment decision을 분리하거나, 사용자 결정의 적용 범위와 상충 분류를 줄이는 우선순위를 정의하고 다중 Session×Activity·부분 확인 사례를 검증해야 한다.

### High — 진행 중 오늘·이번 주는 VALUE와 DATA_INCOMPLETE를 동시에 요구한다 [confirmed]

`business-rules.md` BR-08-02(200~206행)는 현지 날짜 전체가 수집되어야 `COMPLETE`라고 한다. BR-08-05(230~240행)는 현재 일·주에 같은 expected Baseline 식과 `IN_PROGRESS`를 적용하면서 불완전 날짜가 하나라도 있으면 `DATA_INCOMPLETE`이고 Saved를 만들지 말라고 한다. `domain-model.md` DM-18(239~248행)과 `frontend-components.md` FE-C02·FE-02-02(32~43, 177~188행)는 진행 중 값을 전제한다.

### High — MeasurementDay 재기록과 과거 Context 수정의 관찰 갱신 규칙이 없다 [confirmed]

`domain-model.md` DM-14~15(188~211행)는 localDate와 `dailyWasteDurations`를 두지만 날짜별 유일성, revision, source Context 버전이 없다. `service-contracts.md` SC-08-01(301~315행)은 같은 날짜 반복 호출의 생성·대체·거부 의미를 정하지 않고, `business-rules.md` BR-C04(42~56행)는 Context 변경 후 관찰 중 MeasurementDay 갱신을 빠뜨린다.

### High — 목표 화면 누적 진행률과 기간 리포트 합계가 섞였다 [confirmed]

`business-rules.md` BR-09-07(323~333행)은 `accumulated(goal, P)`를 기간 P의 배정 구간 합으로 정의하고 이를 target으로 나눈다. `service-contracts.md` SC-09-07(442~449행)은 `getGoalProgress(period)` 하나만 제공하지만 `frontend-components.md` FE-06-02(271~281행)는 기간 선택 없는 Goal 목록·상세가 소비한다. ### High — 대표 Goal 선택이 파생 segment 좌표 변화에 견디지 못한다 [confirmed]

`service-contracts.md` SC-D04(121~131행)의 ChangeNotifier 작업은 `CREATED|UPDATED|SUPERSEDED`뿐이다. DM-20과 BR-09-03(268~283행)은 완료·취소 때 RunningTimer를 제거하므로 APP-11 변경, 백업, UI 갱신을 공통 계약으로 알릴 `DELETED`가 필요하다.

### Medium — 타이머 취소는 승인되지 않았고 계약도 불완전하다 [confirmed]

FR-8.1·US-17은 시작·완료만 요구하고 Gate 1 Q14도 단일 running timer만 승인했지만 SC-09-04, DM-29, FE-05-02는 취소를 새 기능으로 확정했다. SC-09-04에는 입력, `TIMER_NOT_RUNNING`, dependency failure, 원자성도 없다. 취소가 필요하면 요구 원문·요구사항 승인을 먼저 받고 계약을 완성하며, 아니면 STEP 01 범위에서 제거해야 한다.

### Medium — 비동기 재계산을 허용하지만 조회가 freshness를 반환하지 않는다 [confirmed]

`service-contracts.md` SC-05-02(171행)는 동기 완료 여부를 STEP 02로 넘기되 조회에 계산 상태를 명시하라고 한다. `frontend-components.md` FE-C01·FE-03-02(20~30, 115~119행)는 stale/`RECALCULATING`을 표시하지만 SC-07~09와 SC-Q01~Q04에는 revision, stale, recalculating, failed-recalculation 상태가 없다.
